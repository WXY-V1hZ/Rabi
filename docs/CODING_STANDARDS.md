# 编码规范

供 Agent 编码、审查时使用；与 `AGENTS.md` 配合执行。

## 可读性与模块边界

- **让代码表达业务逻辑**：用业务术语命名数据和操作，用类型表达业务状态，用控制流呈现业务判断和执行顺序。阅读代码时，应能看出操作在什么条件下发生，以及会产生什么结果。注释解释规则的由来和实现中的取舍。
- **减少代码的横向生长**：函数围绕一个明确目的组织，优先使用守卫语句减少嵌套。

## 模块职责与公开接口

- **构建深模块**。围绕明确的业务职责设计模块，用少量贴合调用场景的接口提供完整的操作。接口说明调用所需的输入、可能的结果和必须遵守的约束。模块内部负责协调各个实现步骤，让调用方能直接完成业务操作。
- **每个实现文件承担一项职责**。同一职责的操作和配套定义可以放在同一文件。模块需要拆分实现时，可以使用多个文件，并为调用方提供一个明确的公开入口。单文件模块可以直接以该文件为入口。
- **只导出调用或装配所需的符号**。一个入口可以公开同一职责下的多个相关符号。类型和错误在模块外需要直接引用时才显式导出。内部步骤、辅助函数和仅供内部使用的类型留在实现中。
- **通过公开入口导入**。模块外部从模块入口导入，跨包从包声明的入口导入。模块内部可以直接导入自己的实现文件。功能测试和集成测试使用公开入口，针对内部实现的单元测试可以直接导入该实现。
- **具名转发导出**。多文件模块入口和包入口转发导出时，用 `export { Name } from "…"` 逐项列出公开符号。新增公开符号需要在入口显式声明。

## 测试范围与验证

- **按本轮验收条件写测试**。断言应覆盖本轮交付的行为及需要保留的现有契约。设计讨论中确定的后续行为，在对应的实现任务中加入验收测试。
- **先核对失败断言**。根据本轮验收条件和现有契约判断失败原因。断言超出当前范围时修正测试，实现在范围内违背预期时修正实现。
- **验证后合入**。测试先行时，待对应实现使测试通过，再将两者一起合入 `main`。涉及 PostgreSQL 集成行为的改动，按[本地测试指引](../README.md#运行测试)运行 `pnpm test`，并确认相关集成用例实际执行且通过。

## Effect 错误处理

- **选择结果通道**。正常结果和中间状态使用成功通道，例如无登录会话时返回 `null`。业务拒绝与可预期的依赖故障进入类型化错误通道 `E`。程序自身不变量被破坏时按 defect 处理，取消沿用 Effect 的中断语义。
- **定义具体错误**。Rabi 自定义的内部失败继承基于 `Data.Error` 的 `BaseError`。具体类随所属业务模块定义，方法的 `E` 保留具体错误类型。当调用方需要不同的处理路径时拆分错误类型。
- **固定共同字段**。具体类固定只读的字符串字面量 `_tag` 和诊断 `message`，`_tag` 默认与类名相同。构造时由调用方提供可选的 `cause` 和该错误所需的字段。基类把原始 `cause` 存为 `Redacted<unknown>`，常规日志和序列化默认遮蔽原值。
- **产生与处理失败**。生成器内用 `return yield* new SomeError(...)`，普通函数用 `Effect.fail(...)`。在可能拒绝的第三方 Promise 适配处用 `Effect.tryPromise({ try, catch })` 显式转换，包装时保留原始 `cause`。调用方按 `_tag` 处理认识的错误，例如用 `Effect.catchTag`。
- **在入口转换和记录**。HTTP handler 将内部失败映射为 HTTP 状态码和响应体，CLI 决定面向用户的提示。最终处理依赖故障的入口记录一次 `_tag`、`message` 和可用的关联标识。需要底层诊断时，只提取经过筛选的安全字段。
